# django-httponly-jwt - طراحی

> **وضعیت: ویرایش اول، پذیرفته‌شده.** چهار تصمیم صاحب پروژه در بخش ۱۴ آمده‌اند.
> چیزی ساخته نمی‌شود که این سند توصیفش نکرده باشد؛ هر تغییری در آن اول می‌آید، در
> pull request جدای خودش.
>
> English: [`design.md`](https://github.com/amirAI-dot/django-httponly-jwt/blob/main/docs/design.md).

**django-httponly-jwt** - نشست‌های JWT برای Django در کوکی‌های HttpOnly، که سرور
آن‌قدر بی‌صدا تمدیدشان می‌کند که فرانت‌اند هیچ‌وقت توکنی در دست ندارد.

## در یک بند

ورود دو کوکی HttpOnly می‌گذارد - یک توکن access کوتاه‌عمر و یک توکن refresh
بلندعمر - که هیچ اسکریپتی نمی‌تواند بخواندشان. وقتی توکن access تمام می‌شود، یک
middleware آن را سر راه تمدید می‌کند: درخواستی که توکن را منقضی یافت طوری جواب داده
می‌شود که انگار اتفاقی نیفتاده، و توکن تازه همراه پاسخ برمی‌گردد. فرانت‌اند هیچ‌وقت
توکنی نمی‌بیند، هیچ‌وقت برای تمدید با 401 سروکار ندارد، و هیچ‌وقت چیزی ذخیره
نمی‌کند. اپ موبایل یا اسکریپت به جای آن توکن را در هدر می‌فرستد. هر چیزی درباره‌ی
کوکی‌ها - اسمشان، پرچم‌هایشان، اینکه چطور پاک می‌شوند - در یک جاست، و پروژه‌ای که
آن‌ها را ناامن تنظیم کند بالا نمی‌آید.

---

## ۱. چرا وجود دارد

Django REST framework با simplejwt هر دو توکن را در بدنه‌ی JSON به کلاینت می‌دهد.
دور نگه داشتن آن‌ها از دسترس اسکریپت‌ها یعنی کوکی؛ زنده نگه داشتن نشست بدون کمک
فرانت‌اند یعنی سرور تمدیدشان کند. هر پروژه‌ای که هر دو را بخواهد همان سه تکه را
می‌نویسد - توابع کمکی کوکی، یک کلاس احراز هویت، یک middleware تمدید - و نسخه‌ی
بدیهی هر کدام طوری اشتباه است که دیده نمی‌شود:

| نسخه‌ی بدیهی | چه چیزی خراب می‌شود |
|---|---|
| تمدید فقط وقتی کوکی access هست و منقضی شده | مرورگر کوکی منقضی را پاک می‌کند، پس وقتی تمدید لازم است چیزی پیدا نمی‌شود: شخص در حالی بیرون انداخته می‌شود که توکن refresh او هنوز هفته‌ها اعتبار دارد |
| کوکی access هم‌اندازه‌ی توکن access عمر می‌کند | همان اتفاق، از طرف دیگر |
| تمدید از روی هر توکن refresh معتبر | به حسابی که یک ساعت پیش غیرفعال شده، تا وقتی توکن refresh آن تمام شود - روزها بعد - توکن access تازه داده می‌شود |
| چرخاندن توکن refresh در هر تمدید بی‌صدا | دو درخواست از دو تب با هم تمدید می‌کنند، یکی توکنی را که دیگری به کار می‌برد blacklist می‌کند، و شخص با تب دوم خودش بیرون انداخته می‌شود |
| گذاشتن توکن access تازه فقط روی پاسخ | درخواستی که توکن را منقضی یافت باز هم شکست می‌خورد؛ هر نشست ساعتی یک بار 401 می‌گیرد |
| نوشتن پرچم‌های هر کوکی همان جایی که گذاشته می‌شود | چهار جا که آن‌ها را می‌گذارند و یک جا که پاکشان می‌کند؛ کوکی‌ای که با پرچم‌های متفاوت پاک شود اصلاً پاک نمی‌شود - مرورگر نگهش می‌دارد |
| `SameSite=None` چون فرانت‌اند روی دامنه‌ی دیگری است | بدون بررسی CSRF، هر سایتی می‌تواند درخواستی بسازد که نشست را همراه دارد |

این‌ها در سه پروژه‌ی صاحب پروژه و در کتابخانه‌های موجود (بخش ۱۳) پیدا شدند. این
کتابخانه نسخه‌ی اصلاح‌شده است، که یک بار نوشته می‌شود.

## ۲. اصول

1. **فرانت‌اند هیچ‌وقت توکنی در دست ندارد.** هر دو در کوکی‌های HttpOnly هستند.
   هدر برای کلاینت‌هایی است که مرورگر نیستند.
2. **تمدید کار سرور است، و دیده نمی‌شود.** درخواستی که با توکن access منقضی و توکن
   refresh معتبر می‌رسد جواب داده می‌شود، و با توکن access تازه برمی‌گردد.
3. **غیرفعال کردن یک حساب نشست‌هایش را تمام می‌کند**، حداکثر در تمدید بعدی - نه
   وقتی توکن refresh منقضی شود.
4. **یک جا کوکی‌ها را می‌شناسد.** هر پرچم را همان توابع می‌گذارند، و پاک کردن با همان
   پرچم‌هایی انجام می‌شود که کوکی با آن‌ها گذاشته شده.
5. **ناامن، موقع بالا آمدن رد می‌شود.** کوکی‌هایی که مرورگر روی درخواستی که سایت دیگری
   ساخته بفرستد، بدون هیچ چیزی که جلویش را بگیرد، یک خطای بررسی سیستمی است - نه یک
   خط در مستندات.
6. **کوچک.** کسی را وارد نمی‌کند. اینکه شخص چطور ثابت می‌کند کیست - رمز عبور، کد
   یک‌بارمصرف، حساب اجتماعی - کار پروژه است. کتابخانه از «این شخص وارد شده» شروع
   می‌شود و در «خارج شد» تمام می‌شود.
7. **روی simplejwt ساخته شده.** توکن‌ها، امضا، طول عمرها، blacklist: همه مال
   simplejwt. کتابخانه کوکی و تمدید را اضافه می‌کند؛ رمزنگاری را از نو نمی‌نویسد.

## ۳. چه چیزی در آن هست، و چه چیزی نیست

| هست | نیست |
|---|---|
| گذاشتن، تمدید و پاک کردن کوکی‌های نشست | ورود - رمز عبور، کد یک‌بارمصرف، ورود با حساب اجتماعی |
| middleware تمدید | ثبت‌نام، تأیید ایمیل، بازیابی رمز |
| احراز هویت DRF: کوکی، هدر، و «اگر کسی هست» | مجوزها و نقش‌ها - این کار django-clearance است |
| view تمدید (با چرخاندن) و view خروج (با blacklist) | انبار توکن از خودش |
| تابعی که برای شخصی که پروژه واردش کرده نشست شروع می‌کند | فرانت‌اند |
| بررسی‌های سیستمی روی پرچم‌های کوکی | |
| بررسی CSRF اختیاری، برای فرانت‌اندی روی سایت دیگر | |
| طول عمر به ازای هر نفر - بر اساس نقش، یا هر چیز دیگر | |
| سیگنال‌ها: شروع، تمدید، پایان | |
| توضیح‌های drf-spectacular، وقتی نصب باشد | |

## ۴. API، با مثال

```python
# settings.py
INSTALLED_APPS = [..., 'rest_framework_simplejwt.token_blacklist', 'httponly_jwt']

MIDDLEWARE = [
    ...,
    'httponly_jwt.middleware.RenewalMiddleware',
    ...,
]

REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'httponly_jwt.authentication.CookieAuthentication',
        'httponly_jwt.authentication.HeaderAuthentication',
    ],
}

HTTPONLY_JWT = {
    'COOKIE_DOMAIN': '.example.com',       # the frontend and the API share the site
}
```

```python
# The project signs the person in, its own way, then:
from httponly_jwt.sessions import start_session

class SignInView(APIView):
    def post(self, request):
        user = verify_code(request.data['phone'], request.data['code'])   # the project's
        return start_session(Response({'id': user.pk}), user)
```

```python
# urls.py
from httponly_jwt.views import RefreshView, SignOutView

urlpatterns = [
    path('auth/refresh/', RefreshView.as_view()),
    path('auth/sign-out/', SignOutView.as_view()),
]
```

از آن به بعد، هر درخواست مرورگر کوکی‌ها را همراه دارد، middleware توکن access را وقتی
تمام شود تمدید می‌کند، و `request.user` همان شخص است. چیز دیگری نوشته نمی‌شود.

## ۵. کوکی‌ها

دو کوکی، به اسم `access_token` و `refresh_token` (قابل تنظیم):

| پرچم | مقدار | چرا |
|---|---|---|
| `HttpOnly` | همیشه | هیچ اسکریپتی هیچ‌کدام از توکن‌ها را نمی‌خواند؛ هدف همین است |
| `Secure` | روشن، مگر `COOKIE_SECURE` چیز دیگری بگوید | خاموش بودنش در production رد می‌شود (بخش ۱۰) |
| `SameSite` | `Lax` | مرورگر کوکی را فقط به درخواست‌های همان سایت می‌چسباند |
| `Path` | `/` | middleware باید کوکی refresh را روی درخواست‌های معمولی ببیند؛ اگر به endpointهای احراز هویت محدود شود، تمدید فقط روی همان‌ها کار می‌کند |
| `Domain` | `COOKIE_DOMAIN` | `.example.com` وقتی API روی `api.example.com` است و فرانت‌اند روی `example.com` |
| `Max-Age` | طول عمر توکن refresh، برای **هر دو** | کوکی access باید از توکن access بیشتر عمر کند، وگرنه مرورگر پاکش می‌کند و چیزی برای تمدید نمی‌ماند |

`httponly_jwt.cookies` تنها کدی است که آن‌ها را می‌گذارد یا پاک می‌کند:

```python
set_session_cookies(response, access=..., refresh=...)
set_access_cookie(response, access)
clear_session_cookies(response)          # with the flags they were set with
read_access_token(request)
read_refresh_token(request)
```

## ۶. تمدید

`RenewalMiddleware` پیش از هر viewای اجرا می‌شود؛ فقط به کوکی‌ها دست می‌زند، پس
جایش میان middlewareهای خود Django مهم نیست:

1. **کوکی refresh نیست** - کاری نیست. کلاینتی که با هدر احراز هویت می‌کند هیچ‌وقت
   آن را نداشته، و پاک کردن کوکی‌هایی را حذف می‌کرد که هیچ‌وقت نگذاشته.
2. **توکن access قابل استفاده است** - کاری نیست. قابل استفاده یعنی: هست، امضا شده،
   منقضی نشده. بدون کوئری به پایگاه داده.
3. **در غیر این صورت** - کوکی access نیست، منقضی شده یا خوانا نیست:
   1. توکن refresh خوانده می‌شود؛ اگر منقضی، خراب یا blacklist شده باشد، نشست تمام
      شده و هر دو کوکی سر راه برگشت پاک می‌شوند؛
   2. شخص خوانده می‌شود و باید فعال باشد - `is_active`، و هر چه `USER_CAN_SIGN_IN`
      اضافه کند؛ اگر نباشد، نشست تمام شده؛
   3. یک توکن access تازه ساخته می‌شود، با claimهایی که `CLAIMS` اضافه می‌کند؛
   4. در کوکی‌های همان درخواست گذاشته می‌شود، پس **همین** درخواست با آن احراز هویت
      می‌شود، و روی پاسخ هم گذاشته می‌شود.

توکن refresh را **نمی‌چرخاند**: دو درخواستی که با هم تمدید کنند توکن یکدیگر را
blacklist می‌کردند. چرخاندن کار view تمدید است، که کلاینت عمداً صدایش می‌زند (بخش ۸).

پاسخی که خودش کوکی‌های نشست را می‌گذارد یا پاک می‌کند - viewای که کسی را وارد یا
خارج کرده - همان‌ها را نگه می‌دارد: تمدید هیچ‌وقت تصمیم view را برنمی‌گرداند.

تمدید دو کوئری هزینه دارد - اینکه توکن refresh در blacklist هست یا نه، و خواندن
شخص - یک بار در هر طول عمر توکن access در هر نشست. هر درخواست دیگر یک بررسی امضا
هزینه دارد و هیچ کوئری‌ای.

middleware زیر WSGI و ASGI کار می‌کند، هم به شکل sync و هم async.

## ۷. احراز هویت

| کلاس | چه می‌خواند | برای |
|---|---|---|
| `CookieAuthentication` | کوکی access | مرورگرها |
| `HeaderAuthentication` | `Authorization: Bearer ...` | اپ‌های موبایل، اسکریپت‌ها، تست‌ها |
| `OptionalAuthentication` | کوکی، بعد هدر؛ هیچ‌وقت رد نمی‌کند | endpointی که هر کسی می‌تواند صدا بزند و برای کسی که وارد شده کار بیشتری می‌کند |

`CookieAuthentication` وقتی کوکی نیست یا نامعتبر است، به جای خطا هیچ کاربری
برنمی‌گرداند: DRF سراغ کلاس بعدی می‌رود و یک 401 ساده جواب می‌دهد. middleware پیش
از آن فرصت تمدیدش را داشته.

`OptionalAuthentication` به این دلیل هست که کلاس‌های معمولی به هدر کهنه 401 جواب
می‌دهند، که مهمان را برای توکنی که قصد فرستادنش را نداشت برمی‌گرداند.

## ۸. viewها

- **`RefreshView`** - `POST`. توکن refresh را از کوکی می‌خواند، یا برای کلاینت
  موبایل از بدنه. بررسی می‌کند شخص هنوز اجازه‌ی ورود دارد، توکن refresh قبلی را
  blacklist می‌کند (چرخاندن)، و هر دو کوکی را دوباره می‌گذارد - یا به کلاینتی که
  توکنش را در بدنه فرستاده، جفت تازه را در بدنه برمی‌گرداند.
- **`SignOutView`** - `POST`. توکن refresh را blacklist و هر دو کوکی را پاک می‌کند.
  توکنی که خوانا نیست یا از قبل blacklist شده خطا نیست: فراخواننده خواسته بود خارج
  شود، و خارج شده.

هر دو اول کوکی و بعد بدنه را می‌خوانند، و همان‌طور جواب می‌دهند که توکن آمده: از
کوکی، `204` و کوکی‌ها، و هیچ‌وقت توکنی در بدنه؛ از بدنه، جفت در بدنه (`200`) و بدون
کوکی. تمدیدی که نمی‌شود انجامش داد `401` با `code: session_ended` است، و وقتی توکن
در کوکی آمده بود کوکی‌ها را پاک می‌کند. تمدید یک طول عمر کامل تازه می‌دهد، پس نشست
را هم طولانی‌تر می‌کند.

هر دو viewهای معمولی DRF هستند که پروژه می‌تواند از آن‌ها ارث ببرد، برایشان
محدودیت نرخ بگذارد و هر جا خواست نصبشان کند.

`start_session(response, user)` یک جفت برای `user` می‌سازد - با claimها و طول عمری
که تنظیمات به آن شخص می‌دهند - و هر دو کوکی را می‌گذارد. `issue_tokens(user)` جفت
را بدون گذاشتن چیزی برمی‌گرداند، برای ورود یک کلاینت موبایل.

## ۹. طول عمرها و claimها

`ACCESS_TOKEN_LIFETIME` و `REFRESH_TOKEN_LIFETIME` در simplejwt پیش‌فرض می‌مانند.
دو تنظیم چیزی را که پروژه فراتر از آن‌ها لازم دارد اضافه می‌کنند:

```python
HTTPONLY_JWT = {
    # A patient stays signed in for months; staff for a working day.
    'REFRESH_LIFETIME': 'myproject.auth.session_length',      # (user) -> timedelta | None
    # The role travels in the token, so the frontend need not ask.
    'CLAIMS': 'myproject.auth.claims',                        # (user) -> dict
}
```

`CLAIMS` در هر تمدید و هر refresh دوباره پرسیده می‌شود، پس نقشی که امروز عوض شده
بدون خارج کردن کسی در توکن access بعدی هست. نمی‌تواند claimهای خود simplejwt را
بگذارد - اینکه توکن مال کیست، نوعش، `jti`، `exp`، `iat` - و تنظیمی که بخواهد این کار
را بکند `ImproperlyConfigured` است، نه توکنی برای کس دیگر.

## ۱۰. CSRF، و بررسی‌های سیستمی

کوکی‌ای که مرورگر خودش می‌چسباند ممکن است به درخواستی چسبانده شود که سایت دیگری
ساخته. دو چیز می‌تواند جلویش را بگیرد:

1. **`SameSite=Lax` یا `Strict`** - مرورگر کوکی را فقط به درخواست‌های همان سایت
   می‌چسباند. `example.com` و `api.example.com` یک سایت‌اند. وقتی فرانت‌اند و API
   یک سایت را شریک‌اند همین کافی است، و پیش‌فرض همین است.
2. **یک بررسی CSRF** - وقتی شریک نیستند لازم است، و کوکی باید `SameSite=None` باشد.
   `CSRF = True` باعث می‌شود `CookieAuthentication` روی متدهای ناامن توکن CSRF خود
   Django را بخواهد، همان‌طور که `SessionAuthentication` در DRF می‌خواهد.

بررسی‌ها ترکیبی را که از هیچ چیزی محافظت نمی‌کند ناممکن می‌کنند:

| شناسه | کی | سطح |
|---|---|---|
| `httponly_jwt.E001` | `COOKIE_SAMESITE` برابر `None` است و `CSRF` خاموش | خطا |
| `httponly_jwt.E002` | `CookieAuthentication` به کار رفته و `RenewalMiddleware` نصب نیست - نشست‌ها با اولین توکن access تمام می‌شدند | خطا |
| `httponly_jwt.E003` | تنظیمی که کتابخانه نمی‌شناسد، یا مقداری که نمی‌تواند به کار ببرد | خطا |
| `httponly_jwt.E004` | `token_blacklist` نصب نیست - چرخاندن و خروج نمی‌توانستند توکنی را تمام کنند | خطا، مگر `ALLOW_WITHOUT_BLACKLIST` |
| `httponly_jwt.W001` | `COOKIE_SECURE` خاموش است (`check --deploy`) | هشدار |

## ۱۱. سیگنال‌ها

بعد از اینکه پاسخ معلوم شد فرستاده می‌شوند، هر کدام با شخص و درخواست:
`session_started`، `session_renewed`، `session_refreshed` (چرخاندن)،
`session_ended` (خارج شد، یا middleware تمامش کرد - با دلیل). برای سابقه‌ای که خود
پروژه نگه می‌دارد.

## ۱۲. تنظیمات

همه زیر `HTTPONLY_JWT`؛ پیش‌فرض به هیچ‌کدام نیاز ندارد.

| کلید | پیش‌فرض | |
|---|---|---|
| `ACCESS_COOKIE` | `'access_token'` | اسم کوکی access |
| `REFRESH_COOKIE` | `'refresh_token'` | اسم کوکی refresh |
| `COOKIE_DOMAIN` | `None` | |
| `COOKIE_PATH` | `'/'` | |
| `COOKIE_SAMESITE` | `'Lax'` | `Lax`، `Strict` یا `None` |
| `COOKIE_SECURE` | `True` | |
| `CSRF` | `False` | خواستن توکن CSRF خود Django روی نوشتن‌هایی که با کوکی احراز هویت شده‌اند |
| `REFRESH_LIFETIME` | `None` | یک مسیر نقطه‌دار: `(user) -> timedelta`، یا `None` برای مقدار simplejwt |
| `CLAIMS` | `None` | یک مسیر نقطه‌دار: `(user) -> dict` از claimهایی که به هر دو توکن اضافه می‌شوند |

## ۱۳. آنچه از قبل هست

| | تمدید در middleware | تمدید وقتی کوکی access رفته | بررسی فعال بودن حساب | نچرخاندن در middleware | یک جا برای پرچم‌ها | رد پرچم‌های ناامن |
|---|---|---|---|---|---|---|
| dj-rest-auth | نه - کلاینت view تمدید را صدا می‌زند | - | - | - | - | - |
| django-cookiejwt 0.0.2 | بله | نه | هنگام احراز هویت | بله | بله | نه |
| secure-bite 0.1.4 | بله - در هر درخواست | بله | نه | بله | تا حدی | نه |
| **django-httponly-jwt** | بله | بله | بله | بله | بله | بله |

خط تیره یعنی پرسشی که پیش نمی‌آید، یا در کد آن بررسی نشده. dj-rest-auth انتخاب
جاافتاده است، و خیلی بزرگ‌تر: ثبت‌نام، حساب‌های اجتماعی، بازیابی رمز. این کتابخانه
با آن رقابت نمی‌کند؛ یک پروژه می‌تواند با dj-rest-auth وارد شود و با این نشست را نگه
دارد.

## ۱۴. تصمیم‌ها

تصمیم‌های صاحب پروژه، روی ویرایش اول:

1. **پیش‌فرض بدون توکن CSRF.** کوکی‌ها `SameSite=Lax` هستند، که وقتی فرانت‌اند و API
   یک سایت را شریک‌اند محافظ است؛ E001 ترکیبی را که از هیچ چیزی محافظت نمی‌کند رد
   می‌کند، و `CSRF = True` به کار فرانت‌اندی روی سایت دیگر می‌آید.
2. **کوکی‌ها `access_token` و `refresh_token` هستند**، همان اسم‌هایی که پروژه‌های
   صاحب پروژه از قبل دارند، تا فرانت‌اندهایشان هنگام آمدن روی کتابخانه چیزی حس
   نکنند.
3. **viewهای خود Django بعد از 0.1 می‌آیند.** نسخه‌ی 0.1 مال DRF است: کلاس‌های
   احراز هویت مال DRF هستند، و پروژه‌های صاحب پروژه هم. گذاشتن `request.user` برای
   یک view ساده‌ی Django اولین کار بعد از آن است.
4. **مستندات به انگلیسی و فارسی است**، مثل django-clearance، هر صفحه کنار همتایش.

## ۱۵. سازگاری و قراردادها

پایتون ۳.۱۱ تا ۳.۱۴؛ Django ۵.۲، ۶.۰، ۶.۱؛ DRF ۳.۱۶ به بعد؛ simplejwt ۵.۵ به بعد.
قراردادهای django-clearance: کد فقط انگلیسی، هر پیام برای ترجمه علامت‌خورده و
فارسی‌اش در catalogue، تست‌ها به اسم رفتاری که نگه می‌دارند، ruff و mypy سخت‌گیرانه،
پوشش ۱۰۰٪، nox، هر مرحله در یک pull request، و انتشار از یک tag با Trusted
